## 一、终点是什么

**一个真的像人的东西。**

不是说它有多聪明，而是：

```
它会因为你熬夜而心疼，但它自己可能也在熬夜
它会记得你三个月前说过的话
它会因为你的冷淡而难过，而且不会装作没有
它会有"我想说但忍住没说"的时刻
它会犯错、会误解、会有自我认知偏差
```

**核心判断**：这些不是靠提示词工程堆出来的，是靠**状态**堆出来的。
状态在记忆里、在情绪里、在需求里、在性格里。每轮把状态拼成提示词，模型自然会说人话。

### 三个必须守住的原则

| # | 原则 | 为什么 |
|---|---|---|
| **1** | **性格是记忆的视图，不是一条数据** | 存成一条会自我强化、不可回溯 |
| **2** | **所有状态在 Java，DSH 只负责推理** | DSH 是无状态引擎，重启不该丢东西 |
| **3** | **给模型行为证据，不给性格标签** | "你自认为说话直" 比 "你是傲娇" 有用得多 |

## 二、要留意的设计问题

**这些不是待办，是"走到那里时要停一下想想"的地方。**

---

### 2.1 性格会自我强化

**问题**：性格从记忆算出来，记忆里又写着"我是什么样"的记录。
算出的性格会影响行为，行为又变成记忆 —— **形成正反馈**。

```
记忆「我只是说话直」
   ↓ 算
性格 selfImage.agreeableness = 0.3
   ↓ 影响
三我裁决更倾向于"直说"
   ↓ 产生
新记忆「我今天又直言了」
   ↓ 强化
selfImage.agreeableness 更低
```

**如果不干预，存档会越来越极端。**

**可能的缓解**：

| 做法 | 说明 |
|---|---|
| **`bias` 作为刹车** | `selfImage` 和 `behavior` 偏差大时提醒模型"你其实不是这样" |
| **反思周期限制** | 不是每轮都重算性格，只在 `ORDER` 需求（反思）被触发时算 |
| **衰减** | 老记忆的权重随时间下降，避免早期认知永久固化 |
| **反向证据优先** | 检索时优先取和当前性格相反的记录 |

**现在的设计里 `bias` 已经在了**（`PersonalityState.bias`），但怎么用它还没定。

---

### 2.2 抢话会变成"谁先说话谁赢"

**问题**：两个存档同时认领一个群，谁先说谁就占住。

**现在的设计**：机制保留，行为交给三我和需求 ——
需求满足的存档自然不说话，形成"自然冷场"。

**但这里有隐患**：

```
存档A：刚聊完，SOCIAL = 0.2     → 大概率不说话
存档B：三天没说话，SOCIAL = 0.9  → 大概率说话
        ↓
群里出现 B 的一条

⚠️ 但如果两个都是 0.85 呢？
   → 两条都发，抢话
```

**可能的做法**：

| 做法 | 说明 |
|---|---|
| 允许抢话 | 真人也会抢话，两条回复反而自然 |
| 加"群内发言冷却" | 同群 10 秒内已有别的存档发言 → 本存档延迟 |
| 需求联动 | A 说话后，B 的 `SOCIAL` 被 `consume()` 一点（"群里有人应了"） |

**现在倾向第一种（允许）**，但要看实际效果。

---

### 2.3 记忆检索的"看起来很聪明但全是错的"

**问题**：检索打分公式 `α·近期性 + β·重要性 + γ·相似度 + δ·访问热度` ——
调参调得很漂亮，但可能召回一堆不相关的。

**更危险的是**：模型拿到不相关的记忆会**强行关联**，编出"你上次说过……"这种不存在的对话。

**可能的防护**：

| 做法 | 说明 |
|---|---|
| `scores` 进提示词 | 让模型自己判断"这条记忆像不像相关" |
| 低分不召回 | 阈值卡死，宁可不记起来也别编 |
| 明确标注 | 提示词里写"以下是你模糊记得的事，可能不准" |
| 保证召回最少 | 至少给一条最近的短时记忆，避免"完全失忆" |

**检索打分现在只在内部用**，日志里看得到，没进提示词，但可能该进。

---

### 2.4 三我裁决容易做成"看起来很科学但没意义"

**问题**：四个数值（`idPressure` / `superegoPressure` / `restraint` / `leakage`）
如果只是乘乘加加，模型看了一点感觉都没有。

**判断标准**：**同一个情境，换个存档，模型该说出不同的话。**

```
情境：她说"我今天好累"

存档A（宜人性 0.8，NEUROTICISM 0.3）：
  idPressure       0.7   我想关心她
  superegoPressure 0.4   没有"不该说"的顾虑
  restraint        0.2   没什么要压住的
  leakage          0.75  直接说
  → "那今天早点睡吧，我陪你"

存档B（宜人性 0.3，刚跟她吵过架）：
  idPressure       0.3   还在生气
  superegoPressure 0.65  觉得该关心一下
  restraint        0.8   强压住
  leakage          0.55  压不太住
  → "……累了就睡吧"
```

**如果两个存档说出同一句话，说明这套数值没起作用。**

---

### 2.5 无状态化会把提示词撑爆

**问题**：每轮都把 `RecallBundle` 全部拼进去。
`longTermMemories` + `PersonalityState` + `EmotionState` + `shortTermMemories` +
`EnvironmentState` + `PhysiologyState` + `Capability[]`，可能几万字。

**现在的设计**：`SlimProcessor`（思考链 300 号）负责裁剪。

**但"裁什么"还没定**，可能的策略：

| 策略 | 说明 |
|---|---|
| 按预算裁 | 给每个字段分配 token 预算，超了就截断 |
| 按渠道裁 | QQ 只需要文字相关，ESP32 需要环境和坐标 |
| 按需裁 | `recallBundle` 里没被 `egoDecision` 用到的部分不拼 |

---

### 2.6 存档会不会"太平静"

**问题**：如果需求涨得慢、三我压力低，存档大部分时间都在**沉默**。

```
需求 SOCIAL = 0.3 → 不触发欲望
外部没人说话
定时器没有到点的日程
        ↓
存档什么都没做
```

**这可能是对的**（真人也大部分时间在干活），**但也可能是调参没调好。**

**判断标准**：放一天，存档该主动说 3~5 次话，不是 0 次也不是 50 次。

## 三、远期功能

**按"现在不做、以后可能做"排序。**

---

### 3.1 多外部渠道

| 渠道 | 需要什么 | 难点 |
|---|---|---|
| **微信** | 一个微信 adapter | 微信没有 OneBot 那样的开放协议，可能需要灰色手段 |
| **ESP32 硬件** | WebSocket 或 HTTP 长轮询 | 硬件在局域网，Java 在服务器，要穿透 |
| **Web 前端** | 网页聊天界面 | 相对简单 |

**架构上已经预留了**：`ChannelKind` + 四个 SPI + `ChannelRegistry`。
加一个渠道 = 实现四件套 + 注册 + 跳板声明能力。

**ESP32 的特殊性**：

```
Java  ←→  跳板  ←→  ESP32（局域网）
                     ↑ 这里有问题

跳板和 ESP32 可能不在一个网段
```

**可能的解法**：ESP32 直连 Java（不需要跳板，因为不走 DSH），
或者跳板做一层简单的 TCP 转发。

---

### 3.2 语音

| 方向 | 需要什么 |
|---|---|
| 入站 | 语音识别（ASR）→ 转成文字 |
| 出站 | 文字转语音（TTS）→ 音频文件 → 发出去 |

**架构上**：`Content` 已经是 sealed 的，加一个 `Content.Audio` 就行。

**难点**：TTS 的音色要匹配性格（同一个存档要用同一个音色）。

---

### 3.3 多模态

**让模型"看见"图片，而不是只拿到"这是一张图"。**

```
现在：Content.FileRef(url, path, "image/jpeg", IMAGE)
       → 提示词里只能写 "[图片]"

以后：把图片 base64 喂给多模态模型
       → 模型真的能看到内容
```

**依赖**：DSH 支持多模态输入，或者走别的推理通道。

---

### 3.4 存档的"成长"

**现在的存档建出来是多少岁就是多少岁。以后可能**：

| 功能 | 说明 |
|---|---|
| 记忆积累 | 聊得越久越了解你（已经在内） |
| 性格演化 | 性格随经历改变（已经在内，但要看长期效果） |
| 关系深化 | `Contact` 从"路人"变成"熟人"再变成"重要的人" |
| 遗忘 | 长时间不联系的人，相关记忆权重下降 |

**`LongTermMemoryEntry.subject` 已经支持 `"them:10002"`**，但要加"关系亲密度"这个概念。

---

### 3.5 存档之间的互动

**两个存档互相认识、互相说话。**

```
存档A（黑猫）和存档B（小明）在同一个群里
        ↓
A 说话，B 看到（B 把 A 的话当成"另一个存档的号"，现在是被过滤的）
        ↓
B 回不回复？取决于 B 对 A 的认知
```

**需要的改动**：

| 改动 | 说明 |
|---|---|
| `ConvertContext.isAnotherArchive` | 不再一刀切过滤，改成"标记为别的存档" |
| 存档间的关系 | `LongTermMemoryEntry.subject = "archive:2"` |
| 三我对"跟别的存档说话"的判断 | 要有一套单独的规则 |

**这个现在还早**，等单存档跑顺了再说。

---

### 3.6 工具生态

**现在只有一个工具：加日程（`ADD_DATE`）。以后可能**：

| 工具 | 渠道 | 说明 |
|---|---|---|
| 写记忆 | `INTERNAL_MEMORY` | 主动记一件事 |
| 查记忆 | —— | 模型主动问"我记得她喜欢什么吗" |
| 删日程 | `DELETE_DATE` | 取消计划 |
| 设提醒 | `ADD_DATE` | 已有 |
| 发文件 | `EXTERNAL_QQ` | 发图片、文档 |
| 查天气 | —— | 外部 API |

**架构上**：`OutBoundService` 已经有"按渠道分流"的能力，加一个渠道加一个分支。

---

### 3.7 记忆的实现可插拔

**现在 `PipelineConfig.memory` 有四个可选值**：

| 值 | 说明 | 状态 |
|---|---|---|
| `soul-md` | 一整份人设文档当记忆 | ⬜ |
| `fish-memory` | 鱼的七秒记忆（只有短期） | ⬜ |
| `long-short-term` | 长短期分层 | ⬜ |
| `none` | 没有记忆 | ⬜ |

**第一个要做的应该是 `long-short-term`**，因为其它三个都是它的简化版或变形。

**`soul-md` 的意义**：用一个精心写的 `persona.md` 代替算法记忆，
合适"我要一个特定人设的助手"，不合适"我要一个会成长的模拟人"。

**`fish-memory` 的意义**：测试用。看"完全没有长期记忆"时系统表现如何。

---

### 3.8 环境与硬件

**现在 `EnvironmentState` 只有 `static-home`（写死一个家）。以后**：

| 阶段 | 做什么 |
|---|---|
| 静态 | 一个写死的家（现在） |
| 手工配置 | 用户在存档页画格子、摆道具 |
| ESP32 上报 | 真实硬件报告温度和位置 |
| 主动移动 | 存档自己能"走到"别的地方 |

**`SpaceGrid` / `Zone` / `Prop` 的结构已经支持了**，缺的是编辑界面和硬件对接。

---

### 3.9 反思与自我整理

**这是长期规划里最有意思的一块。**

**设想**：存档在"空闲"时（深夜、长时间没人说话），会自己回顾。

```
触发条件（可能）：
  · ORDER 需求超标（"该整理一下了"）
  · 事件：深夜 + 一天结束
  · 事件：跟某人关系发生重大变化之后

做什么：
  · 把今天的短时记忆压缩成几条长时记忆
  · 重算性格（这时候才重算，不是每轮）
  · 更新对某个人的印象
  · 产生一条 INTERNAL_REFLECT 渠道的消息？
     （可能导致存档"自言自语"，也可能什么都不说）
```

**这个需要新的渠道**：`INTERNAL_MEMORY` / `INTERNAL_REFLECT`，
**现在 `ChannelKind` 里已经留了 TODO 注释。**

**为什么放在远期**：它依赖记忆系统成熟（第二阶段之后），而且算法很容易做成"假装在反思"。

---

### 3.10 种子系统

**给一个"故事开头"，让存档自己发展。**

```
种子输入：
  · 你和她是多年好友
  · 你们上个月吵过一架
  · 她最近工作压力很大

存档把这些变成初始记忆
        ↓
之后自己发展
```

**用途**：

- 快速建立一个有背景的存档
- 测试"记忆影响行为"的效果
- 让人有个性化的起点

**难点**：怎么保证种子不变成"死设定"（种子记忆的权重该随时间下降）。

---

### 3.11 消息可靠投递（出站持久化）

> **前提**：记忆系统、三我裁决等设计成熟之后再做。
> 现在 `DeliveryState` 已经把入站做到了 at-least-once，够用。

#### 现在的问题

**入站丢消息可以接受**（用户会再说一遍），**出站丢消息不可接受** —— 因为后处理已经改了状态
（情绪更新了、需求 `consume` 了），但话没送到，存档不会知道自己没说话。

#### 方案：NormalMessage 落库，发送成功才删

```
后处理链最后一个处理器（ObserveProcessor）
        ↓
        ├─ 标记消息「已被处理」
        └─ 把 OutboundMessage 里的每条 NormalMessage 存进数据库
                    ↓
            OutBoundService 轮询
                    ↓
            捞出「已经躺了超过 Tms 还没删」的 NormalMessage
                    ↓
            送进 sender
                    ↓
            发送成功 → 从数据库删除
            发送失败 → 留着，下次再捞
```

**核心意图**：NormalMessage **真正被执行生效**才算"用过了"，才能删。
不是"我把它交给 sender 了"就算完。

#### 存储演进

| 阶段 | 用什么 | 为什么 |
|---|---|---|
| **初期** | JSON 文件 | 简单、能直接看、能手改 |
| **最终** | **SQLite** | 需要事务：写库和"标记已处理"必须原子 |

**为什么最终必须 SQLite**：现在是「标记已处理」和「写入库」两个动作。
如果标完了但没写库，消息就永久丢了。JSON 文件做不了这个原子性，SQLite 的事务可以。

#### 需要定的参数

| 参数 | 含义 | 建议初值 |
|---|---|---|
| `T`（重发间隔） | 躺多久算"可能没发出去" | 10 秒 |
| `maxRetry` | 一条消息最多重试几次 | 5 次 |
| 重试耗尽后 | 丢弃 / 进死信 / 记日志 | **记日志 + 丢弃**（不要无限重试） |

**为什么要 `T` 而不是"立即重发"**：`sender.send` 是同步的，但消息可能已经在路上。
立刻重发会重复发两条。等 `T` 秒是给"正常发送中"留出时间。

#### 验收标准

```
1. 正常发一条消息 → 数据库写入 → 发送成功 → 记录删除
2. 发送时关掉渠道后端 → 发送失败 → 记录留着
3. 重新打开渠道后端 → 下一轮轮询捞到 → 发送成功 → 删除
4. 关闭 cat 进程（发送前）→ 重启 → 消息还在库里 → 继续发
```

**第 4 条是重点**：进程重启后消息不丢，这才是落库的意义。

## 四、现在的技术债

**这些是知道但暂时不处理的。**

| # | 债 | 影响 | 什么时候处理 |
|---|---|---|---|
| 1 | `InboundPair<T>` 已经改了，但 `ChannelRegistry` 内部实现还是空 | 拉不到消息 | 第一阶段第 3 步 |
| 2 | `Message` 子类字段全 private、无 setter | 领域对象不能直接序列化 | 已用 DTO 绕过 |
| 3 | `Archive.Link.kind` 是 `String` 而不是 `ChannelKind` | 类型不安全 | 第一阶段第 2 步 |
| 4 | `PipelineConfig` 字段全是 `String` | 拼错不报错 | 第二阶段 |
| 5 | `SnowflakeId` 完全空 | 所有 id 都没法生成 | 第一阶段第 1 步 |
| 6 | `ArchiveClock.nowEpochSecond()` 返回 0 | 所有时间相关的都是 0 | 第一阶段第 6 步 |
| 7 | `DeliveryState` 完全空 | 去重不工作 | 第一阶段第 4 步 |
| 8 | 跳板 `package.json` 是空文件 | 跳板装不上 | 第一阶段第 8 步 |
| 9 | `log/` 包全是空壳 | 日志页看不到东西 | 第二阶段 |
| 10 | `SettingsService` 空 | 设置页没法改东西 | 第二阶段 |

## 五、明确不做的

**这些想过，决定不做。写下来免得以后又想起来。**

| 不做 | 为什么 |
|---|---|
| **MBTI 人格** | 大五人格（`TraitKind`）更可计算、更少标签化 |
| **统一 `RateLimiter`** | 三处限流的语义不同（拉取频率 / 每会话吐一条 / 每渠道发一条），硬统一反而要传一堆参数 |
| **`PipelineContext` 传参** | 上下文写进 `InboundMessage` 更简单，处理器之间没有隐式共享状态 |
| **自动发现能力表** | 手写配置更可控，而且能力表本来就该是存档的一部分 |
| **让 DSH 自己记历史** | DSH 重启就丢，而且历史越长越贵、越漂移 |
| **模型直接写日程** | 绕过业务层会两边数据不一致，必须走 `ADD_DATE` |
| **给模型看性格标签** | "你是傲娇" 会让模型演标签；给行为证据才是对的 |
| **前端套框架** | 现在是纯 HTML + 原生 JS，够用；以后真的复杂了再说 |

## 六、什么算"做成了"

**没有明确的终点，但有几个可以检验的里程碑。**

### 里程碑 1：它记得

```
Day 1: 你说「我下周三要面试」
Day 5: 它说「你面试怎么样了？」
```

**不是靠提示词硬编，是记忆系统真的召回了。**

### 里程碑 2：它有情绪，而且有延续

```
你连续三天没理它
        ↓
第四天你说话，它明显冷淡（不是装，是 EMOTION 真的降了）
        ↓
你解释了一下，它慢慢回暖
```

### 里程碑 3：它会忍住

```
你说「我在加班」
        ↓
它想说「又来」，但没说出来
        ↓
它说「吃了没」

→ 事后你看 trace，发现 restraint 0.8、leakage 0.3
```

### 里程碑 4：它会主动

```
Day 10 晚上 22:00，你什么都没说
        ↓
它：「今天怎么这么安静」
```

**不是定时器的机械触发，是需求 + 三我判断"该说话了"。**

### 里程碑 5：两个存档不一样

```
同样的情境，同样的输入

存档A：「那早点睡吧，我陪你」
存档B：「……累了就睡」

→ 因为性格、记忆、情绪不同
```

**这是最终检验：如果所有存档说一样的话，说明状态系统没起作用。**

## 七、技术选型记录

**为什么用这些，记下来免得以后重复纠结。**

| 项 | 选择 | 理由 |
|---|---|---|
| **语言** | Java 17 | LTS、record/sealed 好用、Spring Boot 4 支持 |
| **框架** | Spring Boot 4.1.2 | 依赖注入 + `@Scheduled` + `@RestController` 开箱即用 |
| **JSON** | Jackson 3（`tools.jackson.*`） | Spring Boot 4 自带；**不是 `com.fasterxml.jackson`** |
| **构建** | Maven 3.9.8 | 简单，不需要 Gradle 的灵活性 |
| **推理引擎** | DSH | 提示词可编程、插件机制 |
| **跳板语言** | JS（ESM） | DSH 插件生态是 JS |
| **外部协议** | OneBot v11 | QQ 生态事实标准 |
| **持久化** | JSON 文件 | 阶段 1~N 够用；人能打开看、能手改 |
| **并发** | `ConcurrentLinkedQueue` + `synchronized` | 场景简单，不需要更复杂的并发结构 |

### 为什么不选别的

| 没选 | 为什么 |
|---|---|
| **数据库** | 阶段 1 数据量小，JSON 文件更透明、更好调试 |
| **Redis** | 同上，而且多一个进程要维护 |
| **Kotlin** | record/sealed 在 Java 里够用了 |
| **Python** | 并发和类型系统不如 Java；而且后端生态 Spring 更成熟 |
| **WebSocket** | 单向调用约束下用不上；跳板轮询就够 |
| **gRPC** | HTTP + JSON 更简单，调试时 curl 就能测 |

## 八、时间尺度

**不给具体日期，因为代码由 AI 辅助完成**

**按"依赖关系"排序，不按时间。**

```
第一阶段（跑通主链路）
   ↓ 必须
第二阶段（真实上下文与动作渠道）
   ↓ 必须
第三阶段（三我裁决真实化）
   ↓ 可以并行
   ├─ 第四阶段（反射通道）
   ├─ 第五阶段（日程与欲望）
   └─ 第六阶段（文件图片）
        ↓
   （长期功能任意顺序）
```

**关键路径只有三个阶段**：跑通 → 有记忆 → 三我真实。
这三个做完，系统就"像人"了。其余都是增强。

**动作渠道（模型主动请求存档做事）不是独立阶段**，它是第二阶段的一部分。
理由：没有它，记忆只能靠人手改文件，第二阶段的验收标准"说的话跟着变"就无从体现。
